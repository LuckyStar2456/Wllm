### 2.2 原型必备：数值计量与显示

计量从原型开始进入正常使用路径。首版采用终端状态区和结束摘要即可，不以图形界面为前提；推理输出与指标分开呈现。以下为首版显示设计，后续界面可演进，但必须保持计量口径和记录可比较。

| 必备显示 | 运行中 | 完成或中止后 | 单位与口径 |
|---|---|---|---|
| 当前任务与配置 | 加载/输入处理/生成/结束状态，模型、量化、后端、上下文预算 | 同一请求的有效配置、请求标识与结束原因 | 显示实际生效值 |
| 加载耗时 | 加载阶段已用时间 | 从加载开始至模型就绪耗时；常驻模型标明本次未加载 | s；与进程启动至就绪时间分列 |
| 输入处理 | 输入 token 总数、已处理数、阶段已用时间 | 实际新计算 token 数、耗时和平均处理速度 | token、s、token/s；复用 token 单列，不能算作新计算吞吐 |
| 首 token 延迟 | 尚未生成时显示等待时间；首次生成后固定数值 | 请求接收到首个生成 token 的耗时 | ms 或 s；包括等待、按需加载和输入处理 |
| 生成速度与计数 | 已生成 token 数、最近窗口速度、生成阶段已用时间 | 总生成 token 数、平均持续生成速度 | token、token/s、s；思考 token 计入总生成数 |
| 请求总耗时 | 从接收请求起持续计时 | 请求接收到成功结束或中止/失败的耗时 | s；中止/失败单独标记，不能计作成功回答 |
| 内存 | 推理进程当前工作集、私有提交量、系统可用物理内存 | 各项记录及本次采样工作集峰值 | MiB/GiB；注明进程范围，采样峰值不称精确瞬时峰值 |

计量约定：

- 使用单调时钟记录请求、加载、输入处理、每个目标输出 token 和结束事件；token 按模型 tokenizer/生成事件计数，不以字符、字节或输出刷新次数替代。后续推测草稿与被拒 token 不进入已生成计数。
- 输入处理速度 = 实际新计算的输入 token 数 / 输入处理阶段墙钟耗时。首版须能在输入批次完成时更新进度；不能以整次请求耗时推算输入处理速度。
- 平均持续生成速度 = `(N - 1) / (t_last - t_first)`，其中 N 为目标生成 token 总数，时间戳取 token 在运行时确定的时点。N 小于 2 时显示“不足以计算”，而非 0 或无穷大。另列后端纯计算吞吐时必须标清不同口径。
- 最近窗口速度采用最近 2 秒的目标生成 token 增量 / 窗口实际时长；从首 token 后开始计算，不把首 token 本身计入该窗口增量。窗口不足 2 秒时显示实际时长；生成停顿时数值随窗口变化，不沿用旧值。默认显示和内存采样约每 500 ms 更新，结束事件立即刷新。
- 首 token 指运行时首个生成 token；若能可靠区分思考与正文，再额外显示首个正文可见时间及两类 token 数，不能将两种等待时间混为一项。
- 多进程时注明推理进程 PID，控制进程资源另列；不直接累加可能共享的工作集。GPU 分配、温度、功耗等为可选扩展，核显共享内存不与系统 RAM 相加。
- 尚未发生的事件显示“等待中”；可选指标无法采集时显示“不可用”及原因，不能填 0。上述核心计时、token 计数、输入/生成速度及进程内存须在正常完整请求中实际可用；必备指标缺失不能以占位符通过验收。

每次请求支持保存结构化记录（首版建议 JSONL），包括有效配置、计数、阶段时间、窗口定义、采样周期、资源峰值和结束原因；终端显示与保存记录使用同一份计量数据。重定向文本输出时，指标走独立通道，并保留最终摘要，避免污染模型回答。

原型验收包含：正常生成时可看到数值持续变化；结束摘要与记录一致且可由计数/时间复算；短输出、中止和失败状态无伪造吞吐；多次请求计数重置；计量刷新不阻塞生成。原型阶段用受控事件校验公式并进行实际运行抽查，完整性能矩阵仍留到后续优化阶段。

### 2.3 原型后的逐项推进规则

每个优化项记录所属等级、瓶颈证据、前置条件、预期改善指标、保真约束、最小实验和回退方式。统一流程为：选一项 → 固定对照与阈值 → 实现/配置 → 验证正确性和全流程收益 → 保留或回退 → 更新可运行版本。组合优化必须在单项成立后做消融对照。

等级表示默认投入顺序与依赖，不是要求逐级穷尽全部候选。各级内部按本机收益依据、实现成本和风险排序；每轮围绕有限优化项交付，保留上一版可用路径。

## 3. 比较条件

固定权重摘要、模型/量化、分词器/模板、有效输入 token、上下文、输出上限、停止条件、思考、采样及种子、KV/循环状态和计算精度。

配置上下文与实际输入长度分别记录。未加载、模型常驻无前缀命中、前缀命中分别测；系统文件缓存冷暖另列，进程重启不等于磁盘冷缓存。Ollama 与 Wllm 不同时加载大模型争用内存后再比较。

记录供电、持续负载、温度/频率（可观测时）、背景应用和驱动；交替或随机比较顺序。使用两条参照：用户体验相对现有 Ollama；定制改动相对同提交、同条件且完成调优的上游路径。

跨框架若需要重新量化或转换计算图，先核对等价性；无法等价时归入独立模型/配置对比。不能把上游升级、换小模型或减少输出当作自研收益。

## 4. 工作负载和指标

原型先使用少量固定输入做运行检查，同时提供 2.2 要求的实时数值显示、结束汇总与记录。E2 开始性能比较前，补齐短、中、长输入 × 短、长输出，包含无复用及重复前缀；真实用途样本与合成计算样本分开。具体长度按实际上下文和需求确定，并在对应实验前固定；失败时不自动缩短。

| 指标 | 定义及边界 |
|---|---|
| 启动/加载 | 启动到模型就绪；分列可观测的文件读取、初始化、编译 |
| 输入处理 | 提示词 token/s，记录实际长度及已用上下文 |
| 首 token | 请求发起到首个生成 token，包含排队及输入处理；区分冷/热 |
| 首个可见回答 | 有思考 token 时另列正文等待，不关闭思考来提速 |
| 持续生成 | 解码 token/s、token 间隔和抖动，不以整次耗时倒推 |
| 完整回答 | 请求发起到完成；另列冷启动到完成全程 |
| 资源和稳定性 | 工作集/提交内存、系统/设备内存、缺页、I/O、失败/超时、持续运行 |
| 正确性和质量 | 算子数值、固定前缀 logits 等参照、任务集及长上下文表现 |

llama-bench 用于 pp/tg/组合计算测试，其测量不包含分词和采样，不能替代用户端全流程测量。[上游说明](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md)

固定生成步数与自然停止的完整回答分开；记录实际输出长度。跨 tokenizer 的模型对比还需看完整任务时间和可比文本产出，不能只比 token/s。

## 5. 验收规则

首版原型按 2.1 验收；以下为原型之后优化项的验收要求，不将“证明加速”提前设为原型交付条件。

1. 每项优化实验前固定数值容差、任务质量、噪声和允许回归边界；先过正确性与资源条件再比速度。
2. 启动、首字、解码和全程分别展示；用户没有授权牺牲某项来换另一项。
3. 默认配置须在约定负载上通过质量门槛，各项关键速度无超过约定边界的回归，且至少有可重复的有效改善。部分场景提升仅标为专项候选。
4. 保存原始样本、重复次数、预热和软件版本。分位数附样本量，少量样本不宣称可靠 P99。
5. 检查持续负载、内存增长、取消和恢复；一次成功不是稳定性验收。
6. 推测执行测草稿、验证、回滚、同步、接受率和额外内存；greedy 检验不替代采样分布检验，也不宣称跨后端逐 bit 一致。
7. 精度、模型、上下文或输出改变归入独立配置实验；不通过关闭思考、裁剪专家或丢弃上下文获得默认收益。
8. 无收益候选保存结论并保持关闭，不承诺倍数或绝对双项最优。

记录分为历史已验证结果、研究候选、性能预期，并额外注明源码/元数据核实与上游说明的证据类型。每个性能数字附负载、配置、样本量和来源；预测附假设/范围，不能填入实测列。既有 CPU 的 5% 筛选界线用于该轮噪声与回归判断，不等于“明显加速”的产品标准；后续实验前另定目标，不把讨论中的倍数建议升级为用户要求。

每轮改动完成相关构建、正确性与优化验证后，自动提交并推送到 `origin/main`，同步该轮验收结论。未通过的优化保持关闭或撤回，不作为默认优化发布；推送后核对远端提交。模型、构建产物、本机配置和原始运行日志继续留在本地。

## 7. 用户档位与当前边界

候选表记录模型版本、总/激活参数、精度、上下文、质量、全部速度及资源。在硬约束内展示速度优先、大模型优先与中间配置；更大且不慢的候选不存在时展示真实折中。

首期已完成 E0/E1：固定源码依赖并构建 Windows CPU 原型，只读保留原模型并生成经过字节校验的文本容器。E2 首批已增加模型加载复用、CPU 执行控制和固定阈值的对照工具，结果见 E2 报告。没有下载替代模型或修改 Ollama 配置；完整真实工作负载、长输入质量与跨引擎对照仍需补齐，当前数据不构成跨引擎提速结论。

**Strata 参考边界（2026-10-15 历史筛选，2026-10-17 补充）：** 原筛选记录 RAM 保存专家、GPU 热缓存、CPU 未命中计算及减少重复驻留的 low-RAM 路径，SSD n-gram 表本身不证明权重流式读取。本次另核实其 README 中部分高精度模型在 RAM 不足时从 SSD 读取部分权重的说明，见[参考研究 5.2](engine-references.md#52-strata-资料更新2026-10-17)的固定修订；不再将 RAM 驻留条件概括为全部模式。该资料仍不是本机 16GB/Iris Xe 的运行或速度证据。Wllm E4-05 同时核查此路径与 Colibri，保持完整权重/路由并独立验证；MTP、增量状态和 KV 放置分别进入 E3-04、E3-03、E4-07。

容量实验至少覆盖三种条件：权重可全驻留、只可部分驻留、没有独立 GPU 且容量受限。先用预算限制与小型模型/夹具检验逻辑，再在可获得的真实设备和模型上验收；预算限制不等于已验证真实弱硬件。任何候选均需记录首次加载、首次回答、连续生成、缓存冷暖、长期资源和失败释放。“能加载”“能完成请求”“达到用户等待要求”分别标注。

### 8.5 执行顺序、交付与追踪

近期按以下关口推进，每轮选择有限任务，不要求同时实现所有候选：

1. **资源与能力先行：** E4-01/E5-01 的本机最小子集形成设备去重、共享容量、启动/编译与稳态预算及后端操作矩阵。补齐 E2-01/06 的对应负载与 CPU 参照；资源余量不足不开展正式性能验收。
2. **后端对照：** E2-04 核实后，比较固定 CPU 与可用核显路径的完整/部分放置；先过数值/质量与峰值内存，再比较长输入、无前缀复用、短/长输出及完整请求。工具链、转换和编译成本计入，不预选赢家。
3. **按负载选专项：** 对长输入重点调查 GEMM、复制/同步；对重复前缀先检查 E3-03 完整状态保存/恢复；对生成阶段先检查 E3-04 的文件/接口与回滚条件。兼容性检查可提前，不等于获得实现或收益；通过后才进入相应最小实验，缓存命中与无复用分测。
4. **独立诊断与组合：** E2-02 保持失败重排关闭并定位差异，不阻塞无依赖后端/状态工作。E3-01 以实际张量参照开展，不要求重排先修复；E3-06 只组合已单独成立且状态约束兼容的机制。
5. **容量线另验收：** E4-02 → E4-03/04/05 为 MoE 线，E4-06 为独立 Dense 线，E4-07 按状态瓶颈进入。存储小实验可提前，完整模型实验依赖正确加载/路由/后端；报告容量扩大与延迟收益各自是否成立。纯 SSD 穷举查表不进入近期主线，重启条件见参考研究第 10 节。

E5-02 可随稳定接口准备，完整跨设备自动候选生成/校准保留到 E5-03/04，且只能选择已有可验证能力。近期目标是形成可复现的选择依据，优先争取长输入、重复前缀及生成阶段的实际净收益，不承诺更大参数模型或某种机制必然提速。

每轮围绕有限任务交付，不等全部候选测完。每项记录：任务编号与状态 → 瓶颈证据 → 参考项目及精确文件/提交/许可证 → 复用或重新实现的部分 → 适用硬件/模型 → 用户硬约束 → 实验前阈值与对照 → 实际配置及原始记录 → 数值/质量/性能/资源结果 → 采用、关闭或回退原因。引用设计不能标为已经实现，构建成功不能标为已经提速。

2026-10-17 的交付仅为计划、设计、文件事实与参考资料更新，不构成构建、推理或性能验收。2026-10-21 的资源探测实现与本机验证边界见本轮资源报告；后续各实现任务继续按第 5 节规则完成验证、报告、提交、推送及远端核对。
